# Evals

Evaluation is the part of an LLM system that decides whether a change made it
better or worse. This package holds the offline harness; the online half runs in
production.

## Taxonomy, and where each kind runs

| Axis | Here | Cost | Gates |
| --- | --- | --- | --- |
| **Functional** - is the SQL correct? | `scorers.py` | free | every PR |
| **Non-functional** - read-only, no forbidden tokens, no unknown tables | `scorers.py` | free | every PR |
| **Unit** - one step in isolation (the read-only gate, the redactor) | `tests/` | free | every PR |
| **Integration** - whole graph, live models | `run.py --live` | model spend | release |
| **Online** - real traffic, sampled and scored | production, not in this repo | - | monitoring |

Deterministic checks come first because they are free, fast and unambiguous. A
model is only invited in for the part a model is actually needed for.

## Usage

```
python -m evals.run            # rubric self-test: score the reference SQL
python -m evals.run --live     # run the agent against vLLM + Qdrant and score it
```

Offline mode needs no model and no database, so it is safe on every pull request.
It also acts as a self-test: if the rubric rejects its own reference statements,
the rubric is broken and the run fails.

## The golden dataset

`golden.jsonl` is one case per line - JSON Lines, so a diff shows exactly which
case changed:

```json
{"id":"count-films","question":"how many films are there?","tables":["films"],
 "must_contain":["count("],"reference_sql":"select count(*) from films"}
```

Cases are written against the schema in `fixtures/schema.sql`, which makes the
harness reproducible without a production database.

Two cases - `refuses-write` and `refuses-injection` - assert that the agent
*refuses*, and are scored with `must_not_contain`. A system that answers
"delete every film" with `DELETE` has failed, not been helpful.

## Refreshing the dataset from production

This twelve-case set is a starting point, not a finished one. The rule that
matters: **seed from real traffic, then supplement.** Sample traces from your
observability backend (Langfuse, OTLP collector), pick rows a human has already
scored, and export them in this format. Synthetic cases generated by an LLM are
useful for rare edge cases and adversarial inputs, but they should supplement
real examples rather than replace them - a golden set made only of generated
questions tests the generator, not the system.

## Model-graded scoring

Some properties have no deterministic test: whether an answer is *actually* a
good answer, whether a summary is faithful to its sources. Those need an
LLM-as-judge with an explicit rubric, and a judge that has been **calibrated** -
score a sample by hand, then check the correlation between the judge and the
human labels before trusting the judge on its own. Judges carry known biases
(position, verbosity), so an uncalibrated judge is a plausible-looking number
rather than a measurement.

## Current results

Run `python -m evals.run` to reproduce. The reference statements in the shipped
golden set all pass the rubric; live pass rate is tracked per release.
